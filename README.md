# codyssey_B2-1

# 나만의 용돈 기입장 (`budget_app`)

표준 라이브러리 기반으로 구현한 콘솔형 가계부(`budget_app`) 프로그램입니다. 섹션별로 요구사항과 충족 내용을 나누어 정리했습니다.

---

## 1. 실행 및 입력 방식 (`[충족]` 1번 실행·입력 / `update` 방식 고정)
- **요구사항:** `python -m budget_app <command> [options]` 실행, `--help` 지원, `add` 대화형 입력 및 옵션 기반 명령, `--` 옵션 표기 통일, `update` 방식 문서 고정.
- **충족 내용:** 프로젝트 루트(`codyssey_B2-1`)에서 `python -m budget_app`으로 실행하며, `add`는 대화형(`input()`) 입력, 조회/검색/요약/수정/삭제/내보내기/가져오기는 `--` 옵션 방식을 지원합니다. `update`는 **옵션 기반(`update --id <ID> [--date ...] [--type ...] [--category ...] [--amount ...] [--memo ...] [--tags ...]`)**으로 고정했습니다.

```bash
python -m budget_app --help
python -m budget_app <command> [options]
```

## 2. 데이터 모델 및 저장 정책 (`[충족]` 2번 모델·검증 / 3번 저장 정책)
- **요구사항:** 거래 데이터 모델(`id`, `type`, `date`, `amount`, `category`, `memo`, `tags`) 및 다중 클래스 구조, 입력 검증, JSONL/CSV 포맷 선택, 3개 이상 파일 분리 저장, `./data`(`--data-dir` 변경 가능), 초기 실행 및 빈 카테고리 처리.
- **충족 내용:** 거래 모델과 저장소/서비스/CLI 계층 클래스를 구성하고 입력값 검증을 적용했습니다. 기본 `./data` 폴더(`--data-dir` 변경 가능)에 `transactions.jsonl`, `categories.jsonl`, `budgets.jsonl` 3개 파일로 분리 저장하며, 초기 실행 시 파일 자동 생성 및 기본 카테고리를 제공합니다.

## 3. Import / Export CSV 스키마 (`[충족]` 11번 가져오기/내보내기 스키마)
- **요구사항:** `import --from`, `export --out` (`--month` 또는 `--from`/`--to` 조건), 고정 CSV 스키마(UTF-8, 헤더 포함).
- **충족 내용:** UTF-8 인코딩 및 헤더 포함 CSV 스키마를 고정해 가져오기/내보내기를 지원합니다.

| 열 이름 | 필수 여부 | 설명 |
|---|---|---|
| `date` | Y | `YYYY-MM-DD` |
| `type` | Y | `income` 또는 `expense` |
| `category` | Y | 등록된 카테고리명 |
| `amount` | Y | 양수 정수 |
| `memo` | N | 문자열 |
| `tags` | N | 쉼표(`,`)로 구분된 문자열 |

## 5. 거래 목록 `list`, 예산 `budget`, 월별 요약 `summary` (`[충족]` 5번 `list` / 8번 `summary` / 9번 `budget`)
- **요구사항:** `list` 최신순·`--limit`·제너레이터 스트리밍, `summary` `--month`/`--top` 기반 총 수입·총 지출·잔액·지출 TOP N·데이터 없음 안내, `budget set` 영구 저장 및 `summary` 사용률(%)·초과 경고 출력.
- **충족 내용:** `list --limit 5` 최신순 출력, `budget set`으로 `2026-11` 예산 `20000`원 저장, `summary --month 2026-11 --top 3`으로 총 수입·총 지출·잔액·예산 사용률(`75.0%`)·지출 TOP 3 출력을 확인했습니다.


### 항목 1

#### Q. add/list/search/summary/export/import/update/delete가 요구사항대로 동작하는가?
- `add`, `list`, `search`, `summary`, `export`, `import`, `update`, `delete` 명령을 구현했으며, `add`는 대화형 입력 및 ID 발급, `list`는 최신순 및 `--limit` 지원, `search`는 조건 필터링 및 최신순 출력, `summary`는 월별 총 수입·총 지출·잔액·지출 TOP N 출력, `update`/`delete`는 `--id` 기반 수정/삭제, `export`/`import`는 CSV 내보내기/가져오기를 처리하도록 구성했습니다.

#### Q. 프로그램 재실행 후에도 거래/카테고리/예산 데이터가 유지되는가? (저장 파일 3개 이상)
- 기본 `./data` 폴더(`--data-dir` 옵션으로 변경 가능) 아래에 `transactions.jsonl`, `categories.jsonl`, `budgets.jsonl` 등 3개 이상의 파일로 분리해 영구 저장하므로, 프로그램 종료 후 재실행해도 거래·카테고리·예산 데이터가 유지됩니다.

#### Q. category add/list/remove가 정상 동작하는가? (삭제 시 사용 중인 카테고리 처리 포함)
- `category add`, `category list`, `category remove`를 지원하며, 기존 거래 내역에서 사용 중인 카테고리를 삭제하려 할 때는 삭제를 차단하고 안내 메시지를 출력합니다.

#### Q. budget set이 저장되며, summary에서 예산 사용률/초과 여부가 출력되는가?
- `budget set`으로 월별 예산을 저장할 수 있으며, `summary` 실행 시 설정된 예산 대비 사용률(%)과 예산 초과 시 경고 문구를 함께 출력합니다.

#### Q. import/export가 명시된 CSV 스키마(UTF-8, 헤더, 컬럼)로 동작하는가?
- UTF-8 인코딩 및 헤더 포함 형식으로 `date`, `type`, `category`, `amount`, `memo`, `tags` 컬럼 스키마에 맞춰 CSV 내보내기 및 가져오기를 동작하도록 구성했습니다.

#### Q. 잘못된 입력/파일 오류에서 스택트레이스 없이 오류 메시지와 해결 힌트를 출력하는가?
- 잘못된 입력값이나 존재하지 않는 ID, 파일 관련 예외가 발생하면 스택트레이스를 그대로 노출하지 않고 원인(`오류`)과 조치 방법(`힌트`)을 출력하도록 처리했습니다.

[사진 Q1-6]
- **오류 메시지 및 해결 힌트 출력:** 존재하지 않는 ID 삭제(`TX-999999`)나 사용 중인 카테고리 삭제(`salary`) 등의 오류 상황에서 스택트레이스 대신 원인(`[오류]`)과 해결 방안(`[힌트]`)이 출력됨을 확인했습니다.

#### Q. 오류 상황에서 종료 코드가 0이 아님을 확인할 수 있는가?
- 오류 상황 발생 시 `0`이 아닌 종료 코드(예: `1`)를 반환하도록 구현해 셸(`echo \$?` 등)에서 실패 상태를 확인할 수 있습니다.

### 항목 2

#### Q. 코드가 3개 이상 모듈로 분리되어 있고, 각 모듈의 책임을 "어떻게" 나눴는지 설명할 수 있는가?
- 모델(데이터 구조 정의), 저장소(파일 입출력 및 영구 저장), 서비스(핵심 비즈니스 로직 및 검증), CLI(명령어 파싱 및 입출력), 공통 데코레이터(예외 처리·시간 측정 등) 형태로 역할을 나누어 한 파일에 기능이 집중되지 않도록 분리했습니다.

#### Q. 최소 2개 이상의 클래스에 부여한 책임 경계를 "어떻게" 정했는지 설명할 수 있는가?
- 데이터 레코드의 필드와 기본 검증을 맡는 모델/도메인 클래스와, 파일 저장·조회 또는 업무 규칙 계산을 담당하는 저장소/서비스 클래스를 구분해 데이터 표현과 저장·연산 책임을 분리했습니다.

#### Q. 파일 기반 update/delete를 "어떻게" 안전하게 처리했는지 설명할 수 있는가?
- 수정이나 삭제 시 전체 데이터를 읽어 반영한 뒤 임시 파일에 기록하고 기존 파일과 교체하는 방식(또는 안전 덮어쓰기)을 적용해, 쓰기 도중 문제가 발생하더라도 원본 데이터가 손상되거나 비워지는 위험을 줄였습니다.

### 항목 3

#### Q. list/search를 제너레이터로 스트리밍 처리한 방식을 "어떻게" 구현했고, "왜" 유리한지 설명할 수 있는가?
- 데이터를 한 번에 큰 리스트로 적재하지 않고 제너레이터(`yield`)로 순차 읽으며 필터 조건을 적용해 필요한 항목만 흘려보내는 방식으로 구현했습니다. 데이터가 많아져도 한 번에 점유하는 메모리를 줄일 수 있고, 조건에 맞는 결과를 순차적으로 바로 다루기 유리합니다.

#### Q. 데코레이터로 분리한 공통 기능이 무엇이며, "왜" 분리가 필요했는지 설명할 수 있는가?
- 예외 처리나 실행 시간 측정처럼 여러 명령/함수에 반복되는 공통 관심사를 데코레이터로 분리했습니다. 이를 통해 각 기능 함수의 핵심 로직을 깔끔하게 유지하고, 오류 출력이나 로깅 규칙을 한곳에서 일관되게 관리할 수 있습니다.

#### Q. 타입 힌트를 적용해 얻는 이점을 실제 코드 예로 "어떻게" 확인했고 "왜" 도움이 되는지 설명할 수 있는가?
- 함수 매개변수·반환값과 데이터 필드에 타입 힌트를 지정해 금액(`int`), 날짜(`str`), 선택 값(`Optional` 등)의 기대 형태를 명확히 했습니다. 코드 작성 시 에디터 자동완성이나 타입 점검 과정에서 잘못된 인자 전달·반환 처리 실수를 사전에 줄이는 데 도움이 됩니다.

### 항목 4

#### Q. JSONL과 CSV 중 선택한 저장 포맷의 장단점을 비교하고, "왜" 그 포맷을 택했는지 근거를 말할 수 있는가?
- **JSONL**은 한 줄이 독립된 JSON 객체라 줄 단위 스트리밍 처리가 쉽고 거래·카테고리·예산처럼 성격이 다른 데이터를 각 파일로 관리하기 편하지만, 표 형태(엑셀 등)로 바로 열어보는 직관성은 CSV보다 떨어집니다. 반대로 **CSV**는 표 형태 확인이 쉽지만 태그·메모 등 문자열이나 구조화된 값을 다룰 때 구분자/이스케이프 규칙을 신경 써야 하므로, 프로그램 내부 영구 저장에는 **JSONL**을 선택했습니다.

#### Q. 거래가 10만 건으로 늘어난다면, 현재 구조에서 병목이 어디이며 "어떻게" 개선할지 설명할 수 있는가?
- 거래가 10만 건 이상으로 늘어나면 전체 파일 순회 검색·집계, 월별/카테고리별 반복 계산, 수정·삭제 시 전체 재작성 과정에서 병목이 발생할 수 있습니다. 월별/기간별 파일 분할이나 인덱스/캐시 활용, 집계 연산의 단일 순회 최적화, 변경 빈도가 높은 데이터의 저장·갱신 구조 개선으로 대응할 수 있습니다.

#### Q. import CSV에 일부 깨진 행이 섞이면, "어떻게" 처리해 사용자 신뢰를 지킬지(부분 성공/롤백/리포트) 설명할 수 있는가?
- CSV 가져오기 시 행 단위로 스키마와 필수 값·형식을 검증하면서, 잘못된 행은 건너뛰거나 오류로 분류해 **행 번호와 실패 사유가 담긴 리포트/힌트**를 남기는 방식이 유용합니다. 작업 성격에 따라 유효 행만 반영하고 실패 내역을 명확히 알리거나(부분 성공 + 리포트), 전체 무결성이 중요한 경우 사전 검증 후 일괄 반영/롤백을 선택해 사용자가 결과를 예측하고 신뢰할 수 있게 합니다.
